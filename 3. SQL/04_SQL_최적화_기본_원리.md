# 3장 SQL 최적화 기본 원리

## 1절 옵티마이저와 실행계획

### 1. 옵티마이저(Optimizer)

- 사용자가 작성한 SQL문을 처리하기 위한 여러 실행 방법 중 **가장 효율적이라고 판단되는 실행 방법을 선택**하는 역할
- 옵티마이저가 선택한 SQL 처리 방법을 **실행계획(Execution Plan)**이라고 함

#### 옵티마이저 방식

- **규칙 기반 옵티마이저(RBO, Rule Based Optimizer)**
  - 미리 정해진 규칙과 우선순위에 따라 실행계획을 선택
  - 최근에는 특수한 경우를 제외하고 거의 사용하지 않음
- **비용 기반 옵티마이저(CBO, Cost Based Optimizer)**
  - 여러 실행계획의 예상 비용을 계산하여 **비용이 가장 낮은 실행계획** 선택
  - 현재 일반적으로 사용하는 방식

---

### 2. 비용 기반 옵티마이저(CBO)

- **비용(Cost)** : SQL문 처리에 필요한 예상 시간 또는 자원
- 비용이 낮다고 판단되는 실행계획을 선택
- 인덱스가 존재하더라도 인덱스 스캔의 비용이 더 크다고 판단하면 **테이블 스캔 선택 가능**

#### 비용 계산에 사용하는 정보

- 테이블 정보
- 칼럼 정보
- 인덱스 정보
- 테이블 / 인덱스 통계정보
- 히스토그램 통계정보
- 시스템 통계정보
  - CPU 속도
  - Single Block I/O 속도
  - Multi Block I/O 속도
- 옵티마이저 관련 파라미터

> 정확한 통계정보가 있어야 비용을 보다 정확하게 예측할 수 있음.

---

### 3. 옵티마이저 구성요소

#### ① 질의 변환기(Query Transformer)

- 사용자가 작성한 SQL문을 옵티마이저가 처리하기 쉬운 형태로 변환

#### ② 비용 예측기(Estimator)

- 여러 실행계획의 예상 비용 계산
- 중간 결과집합의 크기, 최종 결과집합의 크기, 데이터 분포 등을 예측
- 정확한 비용 계산을 위해 통계정보가 중요

#### ③ 대안계획 생성기(Plan Generator)

- 동일한 결과를 만들 수 있는 여러 실행계획 생성
- 연산 순서, 연산 방식, 조인 순서 등을 변경하여 대안계획 생성

#### 처리 흐름

`SQL문 → 질의 변환 → 비용 예측 → 여러 실행계획 생성/비교 → 최종 실행계획 선택`

---

### 4. 실행계획(Execution Plan)

- SQL문을 실제로 실행하기 전에 **어떤 방법으로 처리할지 예상한 계획**
- 실행계획에서 주로 확인하는 항목
  - **Operation** : 수행 작업
  - **Name** : 사용되는 테이블 / 인덱스 이름
  - **Cost** : 예상 비용
  - **Rows / Cardinality** : 예상 처리 건수
  - **Predicate Information** : 조건 처리 정보
  - **Access / Filter** : 접근 조건 / 필터 조건

#### 실행계획 읽기

- 일반적으로 **가장 안쪽의 하위 Operation부터 수행**
- 동일한 깊이에 있는 작업은 위쪽 작업부터 처리
- 하위 작업 결과가 상위 Operation으로 전달됨

예)

```text
SELECT STATEMENT
 └─ NESTED LOOPS
     ├─ TABLE ACCESS BY INDEX ROWID
     │   └─ INDEX UNIQUE SCAN
     └─ TABLE ACCESS BY INDEX ROWID
         └─ INDEX RANGE SCAN
```

실행 흐름 예시:

`INDEX UNIQUE SCAN → TABLE ACCESS → INDEX RANGE SCAN → TABLE ACCESS → NESTED LOOPS → SELECT`

---

### 5. 실행계획과 실행내역

#### 실행계획

- SQL문을 실제로 실행하기 전 옵티마이저가 예상한 처리 방법
- Cost 등은 **예상값**

#### 실행내역

- SQL문을 실제로 실행한 후의 처리 정보
- 실제 수행 시간과 처리량 확인 가능

주요 항목:

- **A-Rows** : 실제 처리된 행 수
- **A-Time** : 실제 수행 시간
- **Buffers** : 읽은 블록 수

> 실행계획의 Cost는 실제 수행시간 자체가 아니라 옵티마이저가 실행 경로를 비교하기 위해 계산한 예상값임.

## 2절 인덱스 기본

### 1. 인덱스(Index)

- 검색 조건에 맞는 데이터를 빠르게 찾기 위한 객체
- 책의 **찾아보기(색인)**와 비슷한 역할
- 하나의 테이블은 여러 개의 인덱스를 가질 수 있음

#### 장점

- 조건에 맞는 소량의 데이터를 빠르게 검색 가능

#### 단점

- 인덱스가 많으면 `INSERT`, `UPDATE`, `DELETE` 시 인덱스도 함께 관리해야 하므로 부하 증가

---

### 2. B*Tree 인덱스

일반적으로 많이 사용하는 인덱스 구조

#### 구성

```text
Root Block
    ↓
Branch Block
    ↓
Leaf Block
```

- **Root Block**
  - 가장 상위 블록
  - 다음에 탐색할 Branch Block의 위치 판단
- **Branch Block**
  - 데이터 범위에 따라 탐색 경로 분기
- **Leaf Block**
  - 실제 인덱스 칼럼 값 저장
  - 해당 테이블 행의 위치인 **ROWID** 저장
  - 인덱스 값 순서로 정렬됨
  - Leaf Block끼리 연결된 구조

#### ROWID

- 테이블의 특정 행 위치를 찾기 위한 주소 정보
- 인덱스 Leaf Block에 저장됨

구성 개념:

`ROWID = 데이터 블록 주소 + 로우 번호`

인덱스 검색 과정:

`Root → Branch → Leaf → ROWID → Table Row`

---

### 3. 인덱스 스캔 효율화

복합 인덱스는 **칼럼의 구성 순서**에 따라 스캔 범위가 크게 달라질 수 있음.

- 인덱스 선두 칼럼에서 범위를 많이 줄일 수 있을수록 효율적
- **변별력**이 좋은 칼럼은 특정 데이터를 좁은 범위로 찾기 쉬움
- 변별력 : 전체 데이터 중 서로 다른 값(Distinct Value)이 얼마나 많은지를 나타내는 성질

예)

```text
(시력, 이름, 학년반번호)
```

보다 조건에 따라

```text
(이름, 시력, 학년반번호)
```

처럼 범위를 더 빠르게 줄이는 구성이 유리할 수 있음.

> 인덱스는 존재 여부뿐만 아니라 **조건절과 인덱스 칼럼 순서**가 중요함.

---

### 4. 테이블 랜덤 액세스(Random Access)

인덱스에서 조건에 맞는 데이터를 찾은 후 Leaf Block의 ROWID를 이용하여 실제 테이블 행을 찾음.

`Index Scan → ROWID 확인 → Table Random Access`

- 테이블 랜덤 액세스는 성능 부하 발생 가능
- 인덱스 스캔 범위가 넓어질수록 ROWID를 이용한 테이블 접근 횟수도 증가
- 랜덤 액세스가 지나치게 많으면 오히려 **Table Scan이 더 효율적**일 수 있음

#### 테이블 접근이 필요 없는 경우

SQL문에서 필요한 모든 칼럼이 인덱스에 포함되어 있다면 인덱스만 읽고 결과를 만들 수 있으므로 테이블 랜덤 액세스가 필요하지 않을 수 있음.

---

### 5. 인덱스를 탄다 / 타지 못한다

#### 인덱스를 타는 경우

인덱스의 필요한 범위만 읽어 조건에 맞는 데이터를 찾는 경우

```sql
WHERE birth_date BETWEEN '20070101' AND '20070131'
```

#### 인덱스를 정상적으로 활용하기 어려운 경우

인덱스 칼럼 자체에 함수를 적용하는 경우

```sql
WHERE SUBSTR(birth_date, 5, 2) = '05'
```

- 인덱스에 저장된 원래 값과 변형된 값을 바로 비교하기 어려움
- 필요한 범위만 찾아가는 정상적인 인덱스 범위 스캔이 어려워질 수 있음

> 인덱스가 존재한다고 해서 옵티마이저가 항상 인덱스를 사용하는 것은 아님.

---

### 6. Single Block I/O와 Multi Block I/O

DBMS는 필요한 블록이 메모리의 버퍼 캐시에 있는지 먼저 확인하고, 없으면 디스크에서 읽어옴.

#### Single Block I/O

- 한 번의 I/O에서 **1개의 블록**을 읽음
- 일반적인 인덱스 스캔에 사용
- 인덱스를 통해 테이블을 반복적으로 찾아가면 랜덤 액세스 부하 증가 가능

#### Multi Block I/O

- 한 번의 I/O에서 **여러 개의 연속된 블록**을 읽음
- 일반적인 테이블 스캔에 사용
- 많은 데이터를 한꺼번에 읽을 때 유리

따라서 조회해야 하는 데이터가 많으면 인덱스가 존재하더라도 테이블 스캔이 더 효율적일 수 있음.

---

### 7. 테이블 스캔(Table Scan)

- 테이블의 데이터를 순서대로 읽으며 조건에 맞는 행을 추출
- 일반적으로 **High Water Mark(HWM)**까지 블록을 읽음
- 많은 데이터를 읽을 때 인덱스 스캔보다 효율적일 수 있음

#### 테이블 스캔이 선택될 수 있는 경우

- SQL문에 조건이 없는 경우
- 조건에 사용할 수 있는 인덱스가 없는 경우
- 옵티마이저가 테이블 스캔이 더 저렴하다고 판단한 경우
- 힌트 등으로 테이블 스캔을 강제로 지정한 경우

---

### 8. 인덱스 스캔(Index Scan)

- 인덱스를 이용하여 필요한 데이터의 ROWID를 찾은 후 테이블에 접근
- 대량 데이터 중 **소량의 데이터 조회**에 유리
- 인덱스 스캔 후 테이블 랜덤 액세스가 발생할 수 있음

> 인덱스를 사용했다고 해서 반드시 테이블 스캔보다 빠른 것은 아님.

---

### 9. 인덱스 스캔 종류

#### ① Index Range Scan

- 인덱스의 특정 범위를 읽음
- 조건에 맞는 **1건 이상**의 데이터를 검색할 때 사용
- 필요한 Leaf Block 범위만 읽음

```text
INDEX RANGE SCAN
```

---

#### ② Index Unique Scan

- 유일 인덱스를 이용해 **정확히 1건**을 찾는 방식
- 유일성을 보장하는 인덱스 칼럼에 `=` 조건이 사용되는 경우

```text
INDEX UNIQUE SCAN
```

---

#### ③ Index Full Scan

- 인덱스를 처음부터 끝까지 모두 읽음
- 인덱스의 정렬된 구조를 따라 전체 Leaf Block을 읽음
- 필요한 칼럼이 인덱스에 모두 존재하거나 정렬 특성을 활용할 때 선택될 수 있음
- 인덱스 전체를 읽기 때문에 일반적인 Range Scan보다 비효율적일 수 있음

```text
INDEX FULL SCAN
```

---

#### ④ Index Skip Scan

- **인덱스 선두 칼럼이 조건절에 없어도** 인덱스를 활용하는 방식
- 선두 칼럼의 Distinct Value가 적고
- 후행 칼럼의 변별력이 좋을 때 효과적

예)

```text
INDEX (성별, 고객번호)

WHERE 고객번호 = ?
```

선두 칼럼인 성별 조건이 없어도 성별의 종류가 적다면 각 구간을 나누어 후행 칼럼을 탐색할 수 있음.

```text
INDEX SKIP SCAN
```

---

#### ⑤ Index Fast Full Scan

- 인덱스 전체를 읽는 방식
- **Multi Block I/O** 사용 가능
- 인덱스의 논리적인 정렬 순서를 따라 읽지 않음
- 결과의 정렬 순서를 보장하지 않음
- 병렬 스캔 가능

```text
INDEX FAST FULL SCAN
```

##### Index Full Scan과 차이

| 구분 | Index Full Scan | Index Fast Full Scan |
|---|---|---|
| 읽기 | 인덱스 구조 순서대로 | 물리적 저장 순서 중심 |
| I/O | 일반적으로 Single Block | Multi Block 가능 |
| 정렬 순서 활용 | 가능 | 보장하지 않음 |
| 목적 | 인덱스 순서 활용 | 인덱스 전체를 빠르게 읽기 |

---

#### ⑥ Index Range Scan Descending

- 인덱스 Leaf Block의 연결 구조를 이용해 **뒤에서 앞으로 읽는 방식**
- 기본 Range Scan을 반대 방향으로 수행
- 내림차순 데이터 처리 시 사용 가능

```text
INDEX RANGE SCAN DESCENDING
```

> 최종 결과의 정렬을 확실히 보장하려면 인덱스 스캔 여부와 관계없이 `ORDER BY`를 명시하는 것이 원칙.

---

### 10. Table Scan vs Index Scan

| 구분 | Table Scan | Index Scan |
|---|---|---|
| 사용 조건 | 항상 가능 | 사용할 인덱스 필요 |
| I/O | 여러 블록을 한 번에 읽기 유리 | 일반적으로 1블록 단위 접근 |
| 유리한 경우 | 많은 데이터 조회 | 소량 데이터 조회 |
| 테이블 랜덤 액세스 | 없음 | 발생 가능 |
| 인덱스 필요 | X | O |
| 특징 | 전체 범위 처리 | 필요한 범위를 좁혀 탐색 |

#### 핵심

- **많은 데이터 조회 → Table Scan이 유리할 수 있음**
- **전체 데이터 중 소량 조회 → Index Scan이 유리할 수 있음**
- 인덱스가 존재한다는 이유만으로 Index Scan이 항상 빠른 것은 아님
- 최종 선택은 비용 기반 옵티마이저가 예상 비용을 비교하여 결정

## 3절 조인 수행 원리

### 1. 조인(Join)

- 2개 이상의 테이블 또는 집합을 하나의 결과집합으로 만드는 연산
- 3개 이상의 테이블을 조인하더라도 실제 처리는 **두 집합씩 단계적으로 수행**

예)

```text
A JOIN B
    ↓
결과집합 JOIN C
```

대표적인 조인 방식:

1. **NL Join**
2. **Sort Merge Join**
3. **Hash Join**

---

### 2. NL Join(Nested Loops Join)

첫 번째 집합의 각 행을 기준으로 두 번째 집합에서 조건에 맞는 데이터를 반복해서 찾는 방식

```text
First Table 1행
    ↓
Second Table 검색
    ↓
First Table 다음 행
    ↓
Second Table 다시 검색
```

#### 특징

- 순차적으로 처리
- **부분 범위 처리**에 유리
- 첫 번째 집합의 결과 건수가 적을수록 유리
- 두 번째 집합을 반복해서 조회하므로 인덱스의 영향이 큼
- 테이블 랜덤 액세스 부하 발생 가능
- 조인 순서가 매우 중요
- 온라인 프로그램 / OLTP 환경에 적합

#### 성능을 높이기 위한 조건

- 선행 집합의 데이터 건수를 최대한 줄임
- 후행 집합의 조인 조건에 효율적인 인덱스가 있으면 유리

---

### 3. Sort Merge Join

두 집합을 조인 칼럼 기준으로 각각 정렬한 후 정렬된 결과를 서로 병합하면서 조인

```text
Table A → Sort ─┐
                ├─ Merge → Result
Table B → Sort ─┘
```

#### 특징

- 양쪽 집합을 각각 읽고 정렬한 후 병합
- 인덱스가 없어도 수행 가능
- 기존 인덱스를 이용해 정렬을 생략할 수도 있음
- 정렬 작업에 대한 부하 발생
- 전체 범위 처리에 적합
- 조인 순서의 영향이 상대적으로 적음
- 배치 처리에 사용 가능

---

### 4. Hash Join

첫 번째 집합을 이용해 메모리에 **Hash Table**을 만든 후 두 번째 집합을 읽으면서 Hash Function을 이용해 일치하는 데이터를 찾는 방식

```text
작은 집합
   ↓
Hash Table 생성(Build)
   ↓
큰 집합 Scan(Probe)
   ↓
Hash 비교
   ↓
Result
```

#### 특징

- 작은 집합을 먼저 처리하는 것이 중요
- 첫 번째 집합이 Hash Area 메모리에 들어갈 정도로 작으면 유리
- 정렬 작업이 필요하지 않음
- NL Join처럼 반복적인 테이블 랜덤 액세스 부하가 없음
- 대량 데이터 처리에 유리
- 배치 프로그램, DW, OLAP 등에 적합
- 일반적으로 `=` 조건의 조인에 사용
- 조인 순서가 중요

#### 용어

- **Build Input** : Hash Table을 만드는 선행 집합
- **Probe Input** : Hash Table과 비교하는 후행 집합

---

### 5. 조인 기법 비교

| 구분 | NL Join | Sort Merge Join | Hash Join |
|---|---|---|---|
| 처리 방식 | 순차적 반복 | 정렬 후 병합 | Hash 비교 |
| 처리 범위 | 부분 범위 | 전체 범위 | 전체 범위 |
| 주요 부하 | Random Access | Sort | Hash Area 메모리 |
| 인덱스 영향 | 큼 | 비교적 적음 | 비교적 적음 |
| 조인 순서 | 매우 중요 | 영향 적음 | 매우 중요 |
| 적합 환경 | OLTP / 온라인 | 배치 | 배치 / DW / OLAP |
| 유리한 경우 | 대량 중 소량 조회 | 정렬 후 대량 결합 | 대량 데이터 결합 |

---

### 6. 조인 순서의 중요성

NL Join과 Hash Join은 **선행 집합의 크기**가 매우 중요함.

#### First Table

- 먼저 처리되는 테이블 / 집합
- 조건을 통해 처리 건수를 최대한 줄이는 것이 유리
- 상수값이나 바인드 변수 조건이 존재하면 범위를 줄이기 쉬움

용어:

- NL Join : **Outer Table / Driving Table**
- Hash Join : **Build Input**

#### Second Table

- First Table의 결과값을 받아 뒤에서 처리되는 테이블 / 집합
- NL Join에서는 조인 조건에 사용할 수 있는 인덱스가 중요

용어:

- NL Join : **Inner Table / Driven Table**
- Hash Join : **Probe Input**

#### 최적화된 Join Order

- NL Join : **작은 선행 집합 → 후행 집합 반복 탐색**
- Hash Join : **작은 집합을 Build Input → 큰 집합을 Probe Input**

> NL Join과 Hash Join 모두 일반적으로 선행 집합이 후행 집합보다 작을수록 성능상 유리함.

# 핵심 정리

## 옵티마이저

- SQL문 자체는 **무엇을 가져올지** 표현
- 실제 **어떻게 가져올지**는 옵티마이저가 결정
- 현재는 비용 기반 옵티마이저(CBO)를 주로 사용
- 통계정보를 기반으로 가장 낮은 비용의 실행계획 선택
- 인덱스가 있어도 Table Scan이 더 저렴하면 Table Scan 선택 가능

## 인덱스

- `Root → Branch → Leaf → ROWID → Table`
- Leaf Block에는 인덱스 값 + ROWID 저장
- 복합 인덱스는 **칼럼 순서가 중요**
- 인덱스 스캔 후 Table Random Access가 많아지면 성능 저하
- **Index Scan = 항상 빠름**은 아님
- 소량 조회에는 Index Scan, 많은 데이터 조회에는 Table Scan이 유리할 수 있음

## 조인

- **NL Join** : 작은 선행 집합 + 후행 인덱스 / OLTP / 소량 조회
- **Sort Merge Join** : 두 집합 정렬 후 병합 / 전체 범위 처리
- **Hash Join** : 작은 Build Input + 큰 Probe Input / 대량 처리
- NL Join과 Hash Join은 **조인 순서가 중요**
