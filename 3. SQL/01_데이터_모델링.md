# 01. 데이터 모델링

> SQLD 1과목 - 데이터 모델링의 이해

---

## 1. 데이터 모델의 이해

### 1.1 모델링의 정의

복잡한 현실세계를 일정한 표기법에 의해 표현하는 일.

#### 모델링의 특징

- **추상화**: 현실세계의 다양한 현상을 일정한 양식인 표기법에 의해 표현
  - 모형화, 가설적
- **단순화**: 복잡한 현실세계를 약속된 규약에 의해 제한된 표기법이나 언어로 표현
- **명확화**: 누구나 이해하기 쉽게 대상에 대한 애매모호함 제거

#### 모델링의 세 가지 관점

- **데이터 관점(What, Data)**
  - 업무가 어떤 데이터와 관련 있는지
  - 데이터 간 관계는 무엇인지
- **프로세스 관점(How, Process)**
  - 업무가 실제 하고 있는 일이 무엇인지
  - 무엇을 해야 하는지
- **상관 관점(Interaction)**
  - 업무를 처리하는 방법에 따라 데이터가 어떻게 영향을 받고 있는지

---

### 1.2 데이터 모델링 정의

- 정보시스템을 구축하기 위한 데이터 관점의 업무 분석 기법
- 현실세계의 데이터에 대해 약속된 표기법에 의해 표현되는 과정
- 데이터베이스를 구축하기 위한 분석/설계 과정

#### 기능

- 명세화
- 구조화
- 문서화
- 다양한 관점 제공
- 구체화

#### 중요성

- **파급효과 큼(Leverage)**
- **복잡한 정보 요구사항의 간결한 표현(Conciseness)**
- **데이터 품질(Data Quality)**

#### 유의점

- **중복**: 같은 시간, 같은 데이터 제공
- **비유연성**
  - 사소한 업무 변화에 데이터 모델이 수시로 변경되면 안 됨
  - 데이터 정의를 사용 프로세스와 분리
- **비일관성**
  - 데이터 간 상호 연관 관계를 명확히 정의

#### 데이터 모델링 3단계

```text
개념 데이터 모델링(추상적)
        ↓
논리 데이터 모델링
        ↓
물리 데이터 모델링(구체적)
```

#### 프로젝트 생명주기(Life Cycle)

```text
정보전략계획 → 분석 → 설계 → 개발 → 테스트 → 전환/이행
```

- **개념적 데이터 모델링**
  - 계획/분석 단계
  - 추상화
  - 업무중심적
  - 포괄적
  - 전사적
  - EA 수립 시 사용
- **논리적 데이터 모델링**
  - 분석 단계
  - KEY, 속성, 관계 표현
  - 재사용성 높음
  - 정규화
- **물리적 데이터 모델링**
  - 설계 단계
  - 실제 데이터베이스에 이식할 수 있도록 성능, 저장 등 물리적 성격 고려

---

### 1.3 ANSI/SPARC 데이터 독립성 모델

#### 데이터 독립성의 필요성

- 유지보수 비용 증가 방지
- 데이터 중복성 감소
- 복잡성 증가 방지
- 요구사항 대응 저하 방지

#### 3단계 구조

- **외부 스키마(사용자 관점)**
  - 개개 사용자나 응용프로그래머가 접하는 DB
- **개념 스키마(통합 관점)**
  - DB에 저장되는 데이터와 데이터 간 관계를 표현하는 스키마
- **내부 스키마(물리적 관점)**
  - 물리적 장치에서 데이터가 실제로 저장되는 방법을 표현하는 스키마

#### 2가지 독립성

- **논리적 독립성**
  - 개념 스키마 변경 → 외부 스키마 영향 X
  - 논리적 구조 변경 → 응용 프로그램 영향 X
- **물리적 독립성**
  - 내부 스키마 변경 → 외부/개념 스키마 영향 X
  - 저장 장치 구조 변경 → 응용 프로그램 및 개념 스키마 영향 X

#### 사상(Mapping) 2가지

- **외부적/개념적 사상(논리적 사상)**
  - 사용자가 접근하는 형식에 따라 다른 타입의 필드를 가질 수 있음
- **개념적/내부적 사상(물리적 사상)**
  - 저장된 DB 구조가 바뀌면 개념적/내부적 사상이 변경되어 개념 스키마가 유지됨

---

### 1.4 데이터 모델링의 세 가지 요소

1. **어떤 것(Things)**
   - 엔터티(Entity)
   - 인스턴스(Instance)
2. **관계(Relationships)**
   - 관계(Relationship)
   - 페어링(Pairing)
3. **성격(Attributes)**
   - 속성(Attribute)
   - 속성값(Attribute Value)

---

### 1.5 좋은 데이터 모델의 요소

- **완전성**: 업무에 필요한 모든 데이터가 모델에 정의
- **중복배제**: 하나의 DB 내에 동일한 사실은 한 번만 저장
- **업무규칙**: 많은 규칙을 사용자가 공유하도록 제공
- **데이터 재사용**: 데이터 통합성과 독립성 고려
- **의사소통**: 업무규칙을 엔터티, 서브타입, 속성, 관계 등의 형태로 최대한 자세히 표현
- **통합성**: 동일한 데이터는 유일하게 정의해서 다른 영역에서 참조

## 2. 엔터티(Entity)

### 2.1 개념

- 사람, 장소, 물건, 사건, 개념 등의 명사
- 업무상 관리가 필요한 관심사
- 저장되기 위한 어떤 것(Thing)

### 2.2 특징

- 업무에서 필요한 정보
- 식별 가능
  - 인스턴스 각각을 구분하기 위한 유일한 식별자 필요
- 인스턴스의 집합
  - 하나의 엔터티는 2개 이상의 인스턴스 포함
- 업무 프로세스에 의해 이용
- 속성 포함
- 관계 존재

### 2.3 분류

#### 유무형에 따른 분류

- **유형 엔터티**
  - 물리적인 형태
  - 안정적
  - 예: 사원, 물품, 강사
- **개념 엔터티**
  - 물리적인 형태가 존재하지 않는 개념적 정보
  - 예: 조직, 보험상품
- **사건 엔터티**
  - 업무 수행에 따라 발생
  - 발생량이 많으며 통계자료에 이용
  - 예: 주문, 청구, 미납

#### 발생시점에 따른 분류

- **기본 엔터티**
  - 원래 존재하는 정보
  - 독립적으로 생성 가능
  - 예: 사원, 부서, 고객
- **중심 엔터티**
  - 기본 엔터티로부터 발생
  - 업무에서 중심적 역할
  - 예: 계약, 접수
- **행위 엔터티**
  - 두 개 이상의 부모 엔터티로부터 발생
  - 자주 바뀌거나 데이터가 증가
  - 예: 주문내역, 계약진행

### 2.4 엔터티 명명 규칙

- 현업에서 사용하는 용어 사용
- 약어 사용 X
- 단수 명사 사용
- 유일한 이름 사용
- 생성 의미에 따른 이름 사용

## 3. 속성(Attribute)

### 3.1 개념

- 업무에서 필요한 정보
- 의미상 더 이상 분리되지 않음
- 엔터티를 설명하는 인스턴스의 구성 요소

### 3.2 엔터티-인스턴스-속성-속성값 관계

- 엔터티는 두 개 이상의 인스턴스의 집합
- 엔터티는 두 개 이상의 속성을 가짐
- 속성은 한 개의 속성값을 가짐

### 3.3 분류

#### 특성에 따른 분류

- **기본속성**
  - 업무분석을 통해 바로 정의
  - 예: 제품번호, 제품명, 제조원가
- **설계속성**
  - 업무상으로 존재하지 않지만 설계하면서 도출하는 속성
  - 예: 제조사코드
- **파생속성**
  - 다른 속성으로부터 계산/변형되어 생성
  - 예: 판매금액

#### 엔터티 구성방식에 따른 분류

- **PK(Primary Key)**
  - 엔터티 식별 속성
  - 예: 부서-부서번호, 사원-사원번호
- **FK(Foreign Key)**
  - 다른 엔터티와의 관계에서 포함된 속성
  - 예: 사원-부서번호
- **일반속성**
  - 엔터티에 포함되었지만 PK, FK가 아닌 속성
  - 예: 부서-부서명, 사원-사원명/전화번호

### 3.4 도메인(Domain)

각 속성이 가질 수 있는 값의 범위.

### 3.5 속성 명명 규칙

- 업무에서 사용하는 이름
- 서술식 이름 X
- 약어 사용 제한
- 유일성 확보

## 4. 관계(Relationship)

### 4.1 정의

상호 연관성이 있는 상태. 존재의 형태 또는 행위로서 서로에게 연관성이 부여된 상태.

### 4.2 페어링(Pairing)

- 엔터티 안에 인스턴스가 개별적으로 관계를 가지는 것
- 개별 인스턴스가 각각 다른 종류의 관계를 가지고 있다면 두 엔터티 사이에 두 개 이상의 관계 형성 가능
- **관계 페어링**
  - 각 엔터티의 인스턴스들이 자신과 관련된 인스턴스들과 관계의 어커런스로 참여하는 형태

### 4.3 관계의 분류

- 존재에 의한 관계
- 행위에 의한 관계

### 4.4 관계의 표기법

#### 관계명

- 관계의 이름
- 엔터티가 관계에 참여하는 형태
- 애매한 동사 사용 X
- 현재형 표현

#### 관계차수

- 1:1
- 1:N
- M:N

#### 관계선택사양

- 필수관계
- 선택관계

### 4.5 관계 체크사항

- 두 엔터티 사이에 관심 있는 연관 규칙이 존재하는가?
- 두 엔터티 사이에 정보 조합이 발생하는가?
- 업무기술서/장표에 관계 연결에 대한 규칙이 서술되어 있는가?
- 업무기술서/장표에 관계 연결이 가능하게 하는 동사가 있는가?

## 5. 식별자(Identifier)

### 5.1 개념

엔터티 내에서 인스턴스들을 구분할 수 있는 구분자.

### 5.2 특징

- **유일성**
  - 주식별자에 의해 엔터티 내의 모든 인스턴스를 유일하게 구분
- **최소성**
  - 주식별자를 구성하는 속성의 수는 유일성을 만족하는 최소의 수
- **불변성**
  - 주식별자가 한 번 지정되면 변하지 않아야 함
- **존재성**
  - 주식별자가 지정되면 NULL값 허용 X

### 5.3 분류

#### 대표성 여부

- 주식별자: 대표, 참조관계 연결
- 보조식별자

#### 스스로 생성 여부

- 내부식별자: 엔터티 내에서 스스로 생성
- 외부식별자: 관계를 통해 받아옴

#### 속성의 수

- 단일식별자: 하나의 속성으로 구성
- 복합식별자: 둘 이상의 속성으로 구성

#### 대체 여부

- 본질식별자: 업무에 의해 생성
- 인조식별자: 원조식별자가 복잡해 인위적으로 생성

### 5.4 주식별자 도출 기준

- 자주 이용되는 속성
- 이름으로 기술되는 것 X
  - 명칭, 내역 등
- 복합 구성의 경우 너무 많은 속성 포함 X

### 5.5 식별자 관계

#### 식별자 관계

부모 엔터티로부터 받은 외부식별자를 자식 엔터티의 주식별자로 이용.

- 반드시 부모 엔터티가 생성되어야 함
- 강한 연결관계
- 실선 표기
- 주식별자 속성이 지속적으로 증가하는 구조는 개발의 복잡성과 오류 가능성을 유발

#### 비식별자 관계

부모 엔터티로부터 받은 외부식별자를 부모와 연결되는 속성으로만 이용.

- 부모 없이 자식 생성 가능
- 약한 연결관계
- 점선 표기

# 2장. 데이터 모델과 성능

## 6. 성능 데이터 모델링의 개요

### 6.1 성능 데이터 모델링

성능 향상을 목적으로 설계 단계의 데이터 모델링 때부터 여러 가지 성능 향상 관련 사항이 데이터 모델링에 반영될 수 있도록 하는 것.

예시:

- 정규화
- 반정규화
- 테이블 통합
- 테이블 분할
- 조인 구조
- PK
- FK

#### 특징

- 분석/설계 단계에서 데이터베이스 처리 성능을 향상시킬 수 있는 방법 고려
- 데이터의 증가가 빠를수록 성능저하에 따른 성능개선 비용 증가

### 6.2 고려사항

- 데이터 모델링 시 정규화를 정확하게 수행
- 데이터베이스 용량 산정 수행
- 데이터베이스에서 발생하는 트랜잭션 유형 파악
- 용량과 트랜잭션 유형에 따라 반정규화 수행
- 이력 모델 조정
- PK/FK 조정
- 슈퍼/서브타입 조정
- 성능 관점에서 데이터 모델 검증

---

## 7. 정규화와 성능

### 7.1 정규형

- **제1정규형(1NF)**
  - 모든 속성은 반드시 하나의 값을 가져야 함
  - 중복 제거
- **제2정규형(2NF)**
  - 엔터티의 일반 속성은 주식별자 전체에 종속적이어야 함
  - 부분적 함수종속성 제거
- **제3정규형(3NF)**
  - 엔터티의 일반속성 간에는 서로 종속적이지 않아야 함
  - 이행종속 제거

#### 함수 종속성

데이터들이 어떤 기준값에 의해 종속되는 현상.

- 기준: 결정자
- 종속: 종속자

### 7.2 정규화를 통한 성능 향상 전략

- 데이터를 결정하는 결정자에 의해 함수적 종속을 가지고 있는 일반 속성을 의존자로 하여 입력/수정/삭제 이상현상 제거
- 중복속성을 제거하고 동일한 의미의 일반 속성을 하나의 테이블로 집약
- 한 테이블의 데이터 용량 최소화
- 속도가 빨라질 수도 있고 느려질 수도 있음

| 작업 | 정규화 후 성능 |
|---|---|
| 조회 | 향상 또는 저하 |
| 입력 | 향상 |
| 수정 | 향상 |
| 삭제 | 향상 |

### 7.3 정규화의 장점

- 유연성 극대화
- 재활용 가능성 증가
- 중복 최소화

## 8. 반정규화와 성능

### 8.1 정의

정규화된 엔터티, 속성, 관계에 대해 성능 향상과 개발/운영 단순화를 위해 중복, 통합, 분리 등을 수행하는 것.

### 8.2 반정규화를 고려하는 경우

- 데이터 조회 시 디스크 I/O 양이 많아 성능 저하가 예상되는 경우
- 경로가 멀어 조인으로 인해 성능이 저하되는 경우
- 칼럼을 계산해서 읽을 때 성능 저하가 예상되는 경우

### 8.3 장점

- 일반적으로 조회 성능 향상

### 8.4 단점

- 불필요한 입력(INSERT), 갱신(UPDATE), 삭제(DELETE) 로직 추가
- 데이터 불일치로 인한 정합성 문제
- 불필요한 트랜잭션으로 인한 성능 문제

### 8.5 절차

```text
반정규화 대상 조사
    ↓
다른 방법 유도 검토
    ↓
반정규화 적용
```

- **반정규화 대상 조사**
  - 범위 처리 빈도수
  - 대량의 범위 처리
  - 통계성 프로세스
  - 테이블 조인 개수
- **다른 방법 유도 검토**
  - 뷰 테이블
  - 클러스터링
  - 인덱스 조정
  - 응용 애플리케이션
- **반정규화 적용**
  - 테이블 반정규화
  - 속성 반정규화
  - 관계 반정규화

### 8.6 반정규화 기법

#### 테이블 반정규화

- **테이블 병합**
  - 1:1 관계 테이블 병합
  - 1:M 관계 테이블 병합
  - 슈퍼/서브타입 테이블 병합
- **테이블 분할**
  - 수직분할
  - 수평분할
- **테이블 추가**
  - 중복 테이블 추가
  - 통계 테이블 추가
  - 이력 테이블 추가
  - 부분 테이블 추가

#### 칼럼 반정규화

- 중복 칼럼 추가: 조인 감소
- 파생 칼럼 추가: 계산 감소
- 이력 테이블 칼럼 추가: 조회 향상
- PK에 의한 칼럼 추가: 조회 향상
- 응용시스템의 오작동을 위한 칼럼 추가

#### 관계 반정규화

- 중복 관계 추가
- 테이블/칼럼 반정규화와 달리 데이터 무결성 영향 없음

## 9. 대량 데이터에 따른 성능

### 9.1 대량 데이터 발생에 따른 테이블 분할

- **수직분할**
  - 한 테이블에 많은 수의 칼럼이 있는 경우
  - 칼럼 단위로 분할하여 I/O 감소
- **수평분할**
  - 대용량 테이블을 로우 단위로 분할
  - I/O 감소

### 9.2 대용량 테이블에서 발생하는 현상

#### Row Chaining

로우 길이가 너무 길어 두 개 이상의 블록에 걸쳐 하나의 로우가 저장되는 현상.

#### Row Migration

데이터 블록에서 수정이 발생했을 때 수정된 데이터를 해당 데이터 블록에 저장하지 못하고 다른 블록의 빈 공간을 찾아 저장하는 방식.

> 위 현상으로 많은 블록에 데이터가 저장되면 조회 시 Block I/O 횟수가 증가함.

### 9.3 파티셔닝

- **Range Partition**
  - 범위를 나눔
  - 날짜 또는 숫자 값으로 분리 가능하고 각 영역별 트랜잭션 분리가 가능할 때 적용
- **List Partition**
  - 특정값 지정
  - 지역 단위 파티셔닝 등에 적용
- **Hash Partition**
  - Hash 조건에 따라 해싱 알고리즘을 적용하여 테이블 분리

### 9.4 수평/수직 분할 절차

```text
데이터 모델링 완성
    ↓
데이터베이스 용량 산정
    ↓
대량 데이터 처리 테이블의 트랜잭션 처리 패턴 분석
    ↓
집중화된 단위로 테이블 분리 검토
```

## 10. 데이터베이스 구조와 성능

### 10.1 슈퍼/서브타입 모델

업무를 구성하는 데이터의 공통점과 차이점을 고려하여 효과적으로 표현하는 논리적 모델.

- **슈퍼 타입**: 공통 부분
- **서브 타입**: 공통 부분을 상속받으며 다른 엔터티와 차이가 있는 속성

### 10.2 슈퍼/서브타입 변환 기술

| 구분 | One to One (1:1) | Plus (슈퍼+서브) | Single (All in One) |
|---|---|---|---|
| 트랜잭션 | 개별로 발생 | 슈퍼+서브타입에 발생 | 전체를 하나로 묶어 발생 |
| 특징 | 개별 테이블 유지 | 슈퍼+서브 타입 테이블 | 하나의 테이블 |
| 확장성 | 우수 | 보통 | 나쁨 |
| 조인 성능 | 나쁨 | 나쁨 | 우수 |
| I/O 성능 | 좋음 | 좋음 | 나쁨 |
| 관리 용이성 | 좋지 않음 | 좋지 않음 | 좋음 |

### 10.3 인덱스 특성을 고려한 PK/FK DB 성능 향상

- 트랜잭션 조회 패턴에 따라 PK/FK 칼럼 순서 조정
- 인덱스 선두 칼럼에 대한 조건
  - 가능한 `=` 조건 사용
  - 최소한 `BETWEEN` 조건 사용

## 11. 분산 데이터베이스와 성능

### 11.1 분산 데이터베이스

- 여러 곳으로 분산된 DB를 하나의 가상 시스템으로 사용할 수 있도록 한 DB
- 논리적으로 동일한 시스템에 속하지만 컴퓨터 네트워크를 통해 물리적으로 분산되어 있는 데이터 집합

### 11.2 분산 데이터의 투명성

- **분할 투명성(단편화)**
  - 하나의 논리적 Relation이 여러 단편으로 분할되어 각 단편의 사본이 여러 Site에 저장
- **위치 투명성**
  - 사용하려는 데이터의 저장 장소 명시 불필요
  - 위치 정보가 System Catalog에 유지
- **지역 사상 투명성**
  - 지역 DBMS와 물리적 DB 사이의 Mapping 보장
- **중복 투명성**
  - DB 객체가 여러 Site에 중복되어 있는지 알 필요가 없음
- **장애 투명성**
  - 구성요소(DBMS, Computer)의 장애와 무관하게 트랜잭션 원자성 유지
- **병행 투명성**
  - 다수 트랜잭션 동시 수행 시 결과의 일관성 유지
  - Time Stamp, 분산 2단계 Locking 이용

### 11.3 장단점

#### 장점

- 지역 자치성
- 신뢰성
- 가용성
- 효용성
- 융통성
- 빠른 응답속도
- 통신비용 절감
- 각 지역 사용자의 요구 수용

#### 단점

- 소프트웨어 개발 비용 증가
- 오류 잠재성 증가
- 처리 비용 증가
- 설계/관리 복잡성 증가
- 불규칙한 응답속도
- 통제 어려움
- 데이터 무결성 위협

### 11.4 분산 데이터베이스 적용 기법

#### 테이블 위치 분산

- 테이블 위치를 다르게 배치
- 예: 설계된 테이블을 본사와 지사 단위로 분산
- 위치별 DB 문서 필요

#### 테이블 분할 분산

- 각각의 테이블을 나누어 분산
- **수평분할**
  - 특정 칼럼 기준으로 Row 분리
  - 중복 X
- **수직분할**
  - 특정 칼럼 기준으로 Column 분리
  - 각 테이블에 동일 PK 필요

#### 테이블 복제 분산

동일한 테이블을 다른 지역이나 서버에 동시에 생성하여 관리.

- **부분 복제**
  - 마스터 DB에서 테이블 일부 내용만 다른 지역/서버에 위치
- **광역 복제**
  - 마스터 DB 테이블의 내용을 각 지역/서버에 존재시킴

#### 테이블 요약 분산

지역/서버 간 데이터가 비슷하지만 다른 유형으로 존재.

- **분석 요약**
  - 분산되어 있는 동일한 테이블을 통합하여 전체 요약 정보 산출
  - 예: 판매실적 A사, B사
- **통합 요약**
  - 분산되어 있는 다른 테이블을 통합하여 전체 요약 정보 산출
  - 예: 판매실적 A사-a, B사-b

### 11.5 분산 데이터베이스 설계를 고려해야 하는 경우

- 성능이 중요한 사이트
- 공통코드, 기준정보, 마스터 데이터의 성능 향상
- 실시간 동기화가 요구되지 않는 경우
- Near Real Time 특징을 가진 경우
- 특정 서버에 부하가 집중되어 부하 분산이 필요한 경우
- 백업 사이트를 구성하는 경우
